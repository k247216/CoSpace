# 基于 RocketMQ 的可靠文件清理：设计草案

日期：2026-11-11。状态：设计已确认；截至2026-11-12，数据库模型和事务/引用协调已接入，MQ与实际清理尚未接入。

## 1. 目标与边界

用户彻底删除文件后，清理决定不丢失；存储失败和进程重启后可继续；重复消息安全；并发新增引用不能指向已进入清理阶段的内容。

第一版在现有模块化单体中实现，使用本地存储和 RocketMQ 普通消息。消费者与存储位于同一机器。任务表承担 Outbox 和执行追踪，不使用 Redis 引用计数、不引入全局去重、不改变回收站恢复语义。上传失败留下的无元数据孤儿文件不属于本阶段清理任务的覆盖范围。

## 2. 已选方案与替代方案

- 选择：数据库任务表 + Outbox 补发 + RocketMQ 普通消息。数据库保存清理决定，MQ 驱动执行，任务表记录执行结果并支持恢复。
- 替代：RocketMQ 事务消息 + 本地事务回查。也可协调数据库与消息，但仍需要执行追踪与幂等；本阶段不同时引入两套投递一致性机制。
- 仅数据库任务轮询：可作为更简单的执行方式，但本次明确要学习 MQ，因此轮询仅承担待投递/超时任务的恢复，不绕开消费者直接删除内容。

## 3. 文件生命周期

为 r_pan_file 增加 lifecycle_state：

| 状态 | 语义 |
|---|---|
| ACTIVE | 可以新增用户引用；历史记录迁移为此状态 |
| DELETING | 已确认无引用并决定清理，禁止新增引用 |
| DELETED | 内容已确认不存在，保留物理元数据作为终态记录 |

第一版选择保留 DELETED 元数据，便于对账与追踪；下载和复用查询必须排除非 ACTIVE 记录。物理路径不可被重新用于其他内容。元数据和任务历史的归档另行处理。

DELETING 发生失败后仍保持该状态，不自动恢复 ACTIVE；恢复旧任务不能重新开启引用。

## 4. 清理任务表（r_pan_file_cleanup_task）

| 字段 | 含义 |
|---|---|
| task_id | 主键；同时作为消息业务键 |
| real_file_id | 物理文件 ID，第一版唯一约束，一份物理内容只有一个清理生命周期 |
| storage_type / storage_locator | 不可变的存储实现标识与文件定位快照 |
| execution_state | PENDING / PROCESSING / RETRY / SUCCEEDED / MANUAL |
| delivery_state | PENDING / SENT，独立于执行状态 |
| delivery_attempts / execution_attempts | 投递尝试与消费执行尝试分别计数 |
| next_delivery_at | 下一次允许投递时间 |
| lease_owner / lease_until | 执行租约，恢复处理过程中退出的任务 |
| last_error | 有界、脱敏的最近失败原因 |
| created_at / updated_at / completed_at | 时间记录 |

按 (delivery_state, next_delivery_at) 和 (execution_state, lease_until) 设计扫描索引。具体字段长度、批量大小、重试间隔和上限由实现时确定并配置化。

文件状态与任务执行状态分开：DELETING 是引用准入规则，RETRY 是后台执行结果，两者不可互相替代。

## 5. 事务与并发协议

### 5.1 彻底删除事务

1. 验证操作用户、回收站记录、目录递归范围；禁止删其他用户记录。
2. 收集涉及的物理文件 ID，按 ID 升序锁定物理文件行（SELECT ... FOR UPDATE）。目录记录不对应物理内容，跳过。
3. 重新核对本次待删除引用并删除，检查影响行数。
4. 对每个物理文件做当前读查询剩余引用；所有用户、所有 del_flag 都算引用。
5. 无引用且文件为 ACTIVE 时，更新为 DELETING，同时插入 PENDING 清理任务。
6. 提交；任何一步失败，引用删除、文件状态和任务插入一起回滚。事务内不发消息、不删内容。

注意 MySQL 的事务隔离：普通 COUNT 查询可能使用旧快照。锁定父行后，引用检查必须采用当前读，例如 SELECT file_id ... FOR UPDATE，不能仅凭之前的普通 SELECT 结果作出删除决定。并发测试必须覆盖这个窗口。

### 5.2 所有新增引用路径

普通上传/分片完成、秒传、复制、分享转存都必须通过统一的引用创建协议：在同一个事务中锁定物理文件行，确认 ACTIVE，核对授权，再写入用户文件记录，提交后释放锁。

- 新上传的物理记录在同一事务内新建并新增引用；仍使用统一入口保持约束。
- 批量操作按物理文件 ID 升序取锁，降低交叉等待与死锁风险；死锁回滚仍需正确返回。
- 秒传候选查询只能用于发现候选；取锁后必须重新确认状态与授权，不能信任锁前旧快照。
- 复制/转存重新核对源记录，防止锁前读取的数据已被删除。
- 恢复回收站不新增引用；因为回收站记录始终计入引用数，不应在存在这些记录时转入 DELETING。

仅改删除线程或秒传入口不够，任何绕过协议的新增引用都会破坏保证。

## 6. Outbox 投递

定时扫描已提交、到期、未完成且需要投递的任务。发送普通消息，仅包含 taskId 和事件版本；文件路径不由消息正文决定。

发送成功再条件更新 delivery_state=SENT；失败保留待投递并记录下次时间。若发送成功后进程退出、尚未更新数据库，将再次发送，交由消费幂等处理。

投递逻辑不能覆盖执行终态：消费者可能在发送标记更新前就完成任务。发送结果更新与执行结果更新必须分列、带条件。

定期检查长时间没有完成的 SENT 任务和租约过期的 PROCESSING 任务，重新安排投递。MANUAL、SUCCEEDED 不自动重复补发。MQ 重试耗尽进入死信后，数据库任务仍能被发现；超过应用重试上限转 MANUAL，提供显式重投/恢复方式，不静默丢弃。

## 7. 消费执行

1. 按 taskId 查询任务；未知任务拒绝执行实际删除并记录诊断，终态 SUCCEEDED 消息直接成功。
2. 在短事务中条件领取任务、生成执行令牌与租约，并检查文件为 DELETING；异常状态转人工排查，不能删 ACTIVE 文件。
3. 提交后在数据库事务外执行删除。第一版仅执行 storage_type 与当前本地存储配置一致且规范化后位于允许根目录内的定位；不允许将旧存储路径交给另一个实现。
4. 删除成功或内容已不存在：新事务确认令牌后标记文件 DELETED、任务 SUCCEEDED，再确认消息消费成功。
5. 删除失败：新事务记录原因、次数与重试安排，清除/结束当前租约，并返回消费失败触发 MQ 重试；达到应用上限后保留 MANUAL 任务，不无限自动重试。

租约到期恢复需要条件更新/令牌防止旧执行者覆盖新执行结果。即使两个执行者因超时产生实际存储调用重叠，内容不可再引用或复用其路径，删除不存在文件算成功，保证重复删除安全。

不要使用检查 exists 后无条件认定删除成功的实现；存储接口必须能区分不存在、确实删除成功、权限/IO 等失败。本地实现优先使用可报告结果的文件 API。修复当前忽略 File.delete 返回值、捕获 IO 异常后继续删元数据的问题。

## 8. MQ 与运行安排

保持现有 Spring Boot 2.1.9 / JDK 11 学习基线，不在此阶段同时升级主框架。SDK、Broker 具体版本及接入方式在实现前核对官方兼容信息与本机环境后固定；不直接假定最新 Spring Boot Starter 可兼容。

MQ 不可用时，数据库清理决定仍可提交，任务积压等待投递。模块启动失败与 Broker 暂时离线的处理需明确验证。第一版不独立部署清理微服务；远程消费者访问本地磁盘不在本阶段保证范围。

## 9. 分阶段实现与验收

阶段 A：迁移、文件状态、任务表、所有引用入口协调、删除存储语义。先验证共享引用、回收站保留、事务回滚与并发窗口。

阶段 B：MQ 投递与消费、领取租约、补发、重复消息、失败记录、上限与人工恢复入口。

阶段 C：真实 MySQL 并发测试、真实 Broker 故障测试和单实例本地磁盘演示，保留执行证据。

必须覆盖：

1. A/B 共用内容，A 彻底删除后 B 可下载；B 进回收站仍不清理。
2. 最后一个引用删除后创建任务，事务回滚则无任务且状态恢复。
3. 新增引用先提交则不误删；DELETING 先提交则拒绝新增引用。
4. MQ 不可用时任务保留，恢复后补发。
5. 发送成功但标记未写入，重复消息不破坏状态。
6. 存储异常后任务可重试；已不存在文件重复处理可完成。
7. 标记 DELETING 后进程退出；删除成功但记录结果前退出；重启后均可恢复。
8. 执行租约超时、旧执行者迟到，不能覆盖终态。
9. 错误存储类型/越界路径不执行删除，重试上限后可定位并恢复。
10. 未知 taskId、非法状态不能触发实际删除。

性能压测按用户决定后置；不以 MQ 接入本身宣称吞吐提升，不提前填写延迟或可靠性数字。

## 10. 需要共同确认的产品行为

第一版删除接口的成功含义：用户引用已在数据库中彻底移除，必要的清理任务已经可靠落库；不承诺磁盘空间当场释放。实际内容由后台异步清理，前端先沿用删除后刷新列表的行为。
