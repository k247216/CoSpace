# 秒传授权改造（2026-11-11）

这是一次学习和安全改造记录，不自动作为简历素材。

## 问题与决定

原实现按客户端 MD5 全局查询物理文件，匹配一条就为当前用户建立引用。知道摘要不能证明访问权限；这不是依赖 MD5 碰撞才能触发的问题。

第一版只允许复用当前用户已持有的、未删除且非目录的用户文件引用。授权依据是 `r_pan_user_file.user_id`，不是 `r_pan_file.create_user`。合法分享转存形成引用后也能复用；创建者失去自己的有效引用后不能仅凭创建者身份复用。

## 调用流程

1. 前端提交名称、MD5、size、parentId；登录用户 ID 由后端上下文获取。
2. 请求校验摘要格式、大小非空且非负；Service 也保护直接调用的参数边界。
3. Service 验证目标目录及其祖先属于当前用户、未删除、为目录。根目录有真实记录，0 不是上传目标；循环或断裂目录链拒绝。
4. MyBatis 按 MD5、大小查询物理文件，通过 EXISTS 限定当前用户未删除的文件引用。多条候选按时间和文件 ID 确定选择，不再因为全局重复记录直接失败。
5. 命中时复用物理文件 ID，新建用户文件记录；不新增物理内容或物理文件记录。未命中时前端继续实际上传，不区分未命中的具体原因。

## 当前边界

- 该改造只收紧秒传入口，不代表普通上传、复制、分享等所有入口的权限已统一修复。
- 查询依据源引用记录本身的 del_flag；源文件祖先目录可见性的统一校验另行处理。
- 摘要和大小仍是客户端声明，不等于服务端内容校验；没有实现全局唯一去重或持有证明。
- 按时间选择候选不保证物理内容仍存在；未增加存储存在性检查。
- 未解决新增引用与物理清理间的并发竞争。需要在可靠清理阶段统一协调，不能把本次修改描述为已解决文件生命周期一致性。
- 运行验收前重启后端并刷新前端，使新增 size 参数和后端签名同时生效。
